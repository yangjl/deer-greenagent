TECHNICAL WALKTHROUGH · CURRENT REPOSITORY01 / 20
Start with the simple mental model: DBTL is a governed evidence pipeline. The AI may execute and propose; humans own the scientific decisions. The maize marker, data dimensions, model, and thresholds in this deck are an illustrative experiment. The orchestration, validation, persistence, memory, and review behavior are the current implementation.

THE SIMPLE EXPLANATION02 / 20
DBTL means Design, Build, Test, Learn, with Data Reconciliation as a real gate between Design and Build. “Governed” means a persuasive answer cannot skip an approval boundary. The ordinary chat agent is still available; DBTL is a one-request routing choice inside a project conversation.

01 / worked example · illustrative biology

Can this allele improve yield under drought?

candidate marker chr3:145,678,902 A → G

Does the G allele improve grain yield under managed drought—independent of population structure—without an unacceptable well-watered penalty?

Germplasm1,200 doubled-haploid maize lines
Environments4 sites × 2 years
Treatmentsmanaged drought + well-watered
InputsVCF · phenotypes · pedigree · environments
H₁ β(marker × drought) ≥ +0.25 t/ha and well-watered penalty ≤ 0.10 t/ha

Illustrative domain thresholds. DeerFlow supplies the governance machinery; the project owner must approve the scientific criteria.

DROUGHT-TOLERANCE MARKER VALIDATION03 / 20
The example is intentionally concrete enough to expose every DBTL stage. These files could live in the project workspace as genotypes.vcf.gz, phenotypes.parquet, pedigree.csv, and environments.csv. DeerFlow does not hardcode the mixed model or thresholds. Those become binding only when the human approves the Design package.

ONE REQUEST · ONE TERMINAL BRANCH05 / 20
This is not a second agent replacing ordinary chat. The ordinary node is the compiled lead-agent graph itself. The supervisor is enabled only when dbtl.mode is graph_enabled, the thread belongs to a project, and this request opted in. Every branch terminates, so one user request does not loop among orchestration branches.

Current local configuration: no specialist dbtl_capabilities are declared, so the validated seats resolve to general-purpose stand-ins with distinct focus and briefs.

PREFLIGHT CARD · NO DISPATCH BEFORE ANSWER08 / 20
A one-shot nostream model proposes the roster for this question. Each seat is validated independently: unknown agents, unsupported models, unknown capabilities, and empty briefs are refused rather than silently substituted. Bash is registered as a subagent but explicitly excluded from deliberative seats. Duplicate briefs collapse. If proposal generation fails, the system falls back to deterministic capability selection.

NOSTREAM INTERNAL CALLS09 / 20
Roster drafting and internal council calls are tagged nostream: raw prompts, reasoning, and tool output do not leak into the parent chat or its history. The project context is bounded: it contains a file manifest and structured records, not an unbounded dump of every file. A chair receives an additional structured consensus contract.

08 / execution trace

“Tool call” means three different things here.

MODEL-CHOSEN TOOLS read_file("phenotypes…") bash("python analysis.py") write_file("derived/…") illustrative calls; actual choice depends on the task

Stage workers cannot call taskask_clarificationpresent_files

The model may use filesystem, shell, or configured web/MCP tools allowed by subagent configuration and authorization. The prompt records declared provenance, but orchestration remains server-owned.

SERVER ≠ MODEL ≠ UI SYNTHESIS10 / 20
This distinction prevents an inaccurate “everything is an LLM tool call” explanation. The server assembles context and writes durable packages. The worker chooses among its allowed tools. After successful packaging, the supervisor creates the existing present_files message shape so the frontend can open the artifact inspector.

CONTENT-BOUND APPROVALS12 / 20
Dataset declarations contain URI, SHA-256, immutable flag, and role. The dataset fingerprint is deterministic over the declaration set. Raw data must be declared immutable. Agents may find and propose resolutions, but contradictory sources, trait direction, exclusions, implausible values, leakage, and train/test separation remain human decisions at the write boundary.

REPRODUCIBLE EXECUTION CONTRACT13 / 20
This statistical model is an example, not a built-in StageSpec. The current generic Build spec requires approved Design, approved Reconciliation, and the bound fingerprint. Build produces versioned artifacts and logs; it cannot overwrite raw inputs. The approved Design is injected with its content hash, not merely by path, so later edits cannot silently change the contract.

FAIL-CLOSED VALIDITY ASSESSMENT14 / 20
The generic predictive validity pack checks structure nulls, fold composition, ceiling and direction, leakage, tester holdout, within-group behavior, duplicates/relatedness, reproducibility, and reconciled inputs. Any implausible metric or failed required validity check dominates the headline metrics. Missing required evidence yields inconclusive. The final assessment is human-owned.

CANDIDATE → PROMOTION → PUBLICATION15 / 20
Supported and not-supported outcomes can produce evidence-bound scientific candidates; inconclusive and invalidated outcomes cannot. Promotion and publication are separate human actions. Publication writes SQL audit records, portable Markdown projections, and bounded retrieval pointers. An agent, a stage approval, or a promotion cannot implicitly publish.

DBTL stage workers

Currently receive explicit stage_context, project files, SQL records, tools, and skills—not dynamic memory middleware.

StageSpec declares memory read/write policies, but the current LiveStageAdapter does not yet enforce those policies or inject dynamic memory into workers. Memory is never scientific evidence by itself.

CHAT CONTEXT ≠ STAGE EVIDENCE16 / 20
This is an important implementation detail. Project memory is keyed by user and project. Memory learning excludes tool chatter and uses only current-run messages. DBTL worker execution uses a different middleware chain, so evidence comes through explicit stage context and durable artifacts. Published knowledge can later become a governed retrieval pointer for project conversation.
