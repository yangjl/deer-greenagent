PLAN WALKTHROUGH · docs/plans/2026-07-28-design-deck-feedback-plan.md01 / 18
This deck walks the proposed plan, not shipped behavior. Nothing in the repository implements it yet. The plan is deliberately opinionated about one thing: a page rendered by an agent may collect a decision, but it must never be the thing that authorizes it. Everything else in the plan follows from that split.

01 / the problem

One decision currently lives in three places.

A design meeting ends, and the owner has to assemble the decision from surfaces that each hold part of it.

surface 1 · read only The slide deck

Renders the recorded chair result — agreements, contested points, synthesis. It cannot collect anything, and it tells the owner to go to the review sheet.

council_deck.render_council_deck
surface 2 · in chat The clarification card

A paused chair raises a standard ask_clarification. Answering it in chat resumes only the chair, over the positions already recorded.

human-input-card.tsx
surface 3 · in the rail The Design review sheet

Owns submit-for-review and the approve / request changes / reject verdict. It is the only place a durable, revision-bound review can be written.

project-rail/design-review.tsx
THE COST

The evidence, the question, and the authority to answer it are three different screens. Even the chat shortcut just points back at the sheet.

WHY THIS PLAN EXISTS02 / 18
Worth naming the most recent change here: the stabilization commit made explicit review language in cycle-scoped chat a deterministic control boundary, so typing "approve" no longer invokes a model — it immediately directs the reviewer to the revision-bound project review action. That was the right fix, and it is also a fourth pointer at the same sheet. The plan's argument is that the pointer should not be necessary.

ONE SURFACE, UNCHANGED AUTHORITY03 / 18
"Only input surface" is a claim about where a person types, not about where evidence lives. The Markdown package, the JSON package, the worker record, and the activity feed all stay readable — the deck may link or open them. Removing the sheet must not remove the evidence.

03 / how this plan was made

Three positions, kept intact.

independent position Product & interaction
  • One contextual surface beats a deck plus a card plus a sheet.
  • Open on the decision that needs the owner.
  • Keep drafts through a retry; freeze accepted answers.
  • State which conversation will resume.
  • Keep meeting feedback distinct from formal stage review.
independent position Architecture & governance
  • The HTML stays an untrusted projection.
  • It emits bounded intents; the parent maps them to fixed handlers.
  • A server-issued descriptor binds project, cycle, attempt, round, thread, request, artifact, and hashes.
  • Keep submit_for_review and stage_review as explicit transitions.
red team How this gets abused
  • A generic HTML write bridge lets any agent page imitate a Design deck.
  • A downloaded deck can be framed by a hostile page.
  • An old tab can submit against a later round.
  • A truncated deck could claim the reviewer read a different document.
The debate did not support an invisible one-click submit-and-approve. Two frontend mutations presented as one atomic action can half-complete; a future one-click action must be a single server command.
DISAGREEMENT BEFORE SYNTHESIS04 / 18
This slide follows the same rule the plan's own review Markdown follows: show where the positions disagreed before showing what was concluded. The red-team column is not decoration — every fail-closed rule later in this deck traces back to one of those four attacks.

04 / chair synthesis

Adopt the deck — under five constraints.

The conditions that make "the deck is the input surface" safe
  1. The persisted HTML starts inert. It becomes interactive only after an authenticated parent validates a server-issued descriptor against current hashes and state.
  2. The deck stays a pure renderer. Scientific option text comes from a validated chair result; workflow action text comes from server-owned vocabulary.
  3. Canonical Markdown and JSON remain the evidence record; the exact deck is a separately hashed projection. A review binds both.
  4. A paused chair resumes only in the conversation that produced the deck. Opening another chat or another cycle stays independent.
  5. The Design sheet survives behind a rollback flag until parity and live-state migration are proven.
Why "pure renderer" is load-bearingIf the deck could write a sentence of its own, an approval could bind to prose no participant argued for.
Why the hash split mattersAn audit must answer two questions: what evidence was authoritative, and what did the reviewer actually look at.
ADOPT, WITH CONDITIONS05 / 18
Constraint one is the whole security model in a sentence. Constraint five is the operational one people forget: this feature removes the only working review path, so the old path has to remain reachable until live surfaces have actually migrated and rollback has been exercised at least once.

ELEVEN STATES, ONE RENDERER06 / 18
Notice how few rows are actionable — three. Every other row exists to make a wrong action impossible rather than merely discouraged. The last two rows are the ones that turn a class of security bugs into a visible error message.

06 / option and comment rules

What the deck may ask, and what it must require.

Chair feedback
  • Exactly one option is selected in the first version.
  • No option is preselected — not even a recommended one.
  • A recommendation may be labelled and explained as recorded evidence.
  • The comment is optional.
  • An “Other” option requires text.
  • No valid structured options? Show the exact recorded question with free text.
Formal review
  • “Submit for review” takes no comment.
  • Approve permits an optional comment — the action and bindings are already structured facts.
  • Request changes requires a comment or an explicitly selected contested card.
  • Reject requires a comment.
  • The backend never manufactures prose and attributes it to the reviewer.
AUTHORSHIP

The selected action and the human's comment are stored separately. Any readable sentence assembled from them is labelled rationale_source = server_projection.

NO PRESELECTION · NO MANUFACTURED PROSE07 / 18
Two rules here are ethical, not technical. Not preselecting the recommendation keeps a default from becoming a decision nobody made. Keeping the human comment distinguishable from the server's readable projection means a future auditor can tell what a person actually wrote from what the system wrote on their behalf.

07 / continuity

Work continues where it started. Nothing gets locked.

Guaranteed
  • Every surface names its originating conversation.
  • Chair feedback and requested changes continue only there.
  • The deck says where work will continue and offers a link.
  • A resumed chair updates that thread's normal badge without interrupting the active chat.
Forbidden
  • No project-global “waiting for you” modal.
  • No pending-input lock or composer lock.
  • No automatic thread switch.
  • No substitute thread created when the deck is opened from elsewhere.
INVARIANT

The owner may leave that conversation, open a new chat, and start another cycle while the first meeting waits. A pending decision is not a mode.

A PENDING DECISION IS NOT A MODE08 / 18
Opening the deck from another project view may display it, but mutation is allowed only when the descriptor still resolves to the originating project, cycle, and thread. Display and authority are separate questions, and conflating them is how you end up with a substitute thread that owns nothing.

TWELVE INVARIANTS · THE THREE THAT CARRY THE REST09 / 18
The plan lists twelve invariants; these three do most of the work. The subtle one is the middle: it is tempting to treat the parent's validation as the security boundary because it is the one you can see failing in the UI. It is not. If the server ever trusts the parent's word, the whole model collapses to "any page that can talk to the parent can write".

09 / durable contract · 1 of 2

A paused chair returns structure, not a sentence.

    "version": 1,
    "id": "validation-population",
    "options": [
      { "id": "family_holdout",
        "label": "Family holdout", … },
      { "id": "random_split",
        "label": "Random split", … }
    ],
    "recommended_option_id": "family_holdout",
    "recommendation": "Matches the stated
       deployment population."
  }
}
Validation must
  • allow one focused request per chair pause
  • require stable, bounded, unique option IDs
  • require 2–5 options for card mode
  • bound labels, values, descriptions, recommendation text
  • reject a recommended_option_id that is not present
  • preserve the existing exact clarification_question
  • fail the contract or fall back to free text by explicit, test-covered policy
It must never silently drop the question. A malformed decision request costs the card layout — not the chair's ability to ask.

The chair-resume prompt receives a mechanical rendering of the selected value and comment; the structured response stays in metadata so the exact human choice never depends on parsing prose later.

STRUCTURED QUESTION → STRUCTURED ANSWER10 / 18
This is what makes option cards possible at all. Today the chair asks a question as a string and the card renders it. To render real choices you need the choices to exist as data — and once they exist as data, the audit record can say which one a person picked, rather than requiring someone to re-read a sentence years later.

THE DECK IS A PROJECTION, NOT THE EVIDENCE11 / 18
The warning in the corner is a real bug waiting to happen. The moment a deck is just another artifact on the attempt, "approve the latest artifact" starts approving the slides instead of the reviewed document. Type and revision, never recency.

11 / sandboxed bridge

Six steps before a single control is enabled.

1deck → parentEmits ready with a protocol version and its public surface_id. Nothing else is known to it.
2parentChecks event.source is the exact iframe contentWindow.
3parentResolves the selected file to a registered Design surface and verifies its content hash.
4parent → serverFetches the authenticated surface read model: status, allowed actions, revisions, hashes, receipts.
5parent → deckCreates a random per-mount channel ID and sends initialize with current status and allowed actions.
6every message afterMust match source window, channel ID, protocol schema, surface ID, and allowed action set.

Messages carry no endpoints and no credentials. postMessage("*") is acceptable only because no secret crosses the boundary — and the channel ID is convenience, not authorization.

HANDSHAKE → BOUNDED VOCABULARY12 / 18
The vocabulary is deliberately tiny. Four intents up, five states down. A closed enum is what stops an attacker-authored page from being creative: there is no message that means "call this endpoint", only messages that mean "the person pressed the button you told me about".

12 / mutation

Two paths. Both already exist; both get bound tighter.

path A Paused chair
  1. The surface references the exact server-emitted Human Input request.
  2. The parent submits the existing human_input_response shape through the originating thread's hidden reply path, plus surface_id and client_submission_id.
  3. The server confirms it is the newest unanswered linked request, consumes it once, and starts or replays the same bound run.
  4. The supervisor keeps using clarification_answer — so only the chair resumes, over the recorded positions.

Idempotency at (thread_id, request_id, client_submission_id). Run concurrency alone does not stop duplicate hidden human messages.

path B Final Design gate
  1. submit_for_review uses the existing stage transition, extended to validate surface, evidence revision/hash, and deck hash.
  2. Only after the server returns awaiting_review does the same deck enable the three verdict cards.
  3. A verdict uses the existing authenticated review transition, extended with Design deck provenance.
  4. Request changes records exact issue IDs and comment, then queues the focused refinement in the originating conversation. Approve and reject start no run.

Two visible transitions, deliberately. A one-click version would need one atomic server command.

REUSE THE TRANSITIONS · BIND THEM HARDER13 / 18
Neither path invents a new way to mutate DBTL state. That is the point — the existing transitions already enforce membership, reviewer identity, expected revision, and idempotency. What is new is that each write now also names the exact deck the human was looking at when they decided.

NO REBASING

A response rejected for stale DB, stage, artifact, deck, policy, or projection revision is never automatically retried against the new revision. The human decided about a specific document.

Slack and other IM channels cannot host the interactive deck — they get an authenticated deep link and a read-only summary. The Design gate is documented as web-only rather than left apparently actionable in chat.

FOURTEEN CONDITIONS · NONE OF THEM SILENT14 / 18
The no-rebasing rule is the one worth defending in review. Auto-retrying against a newer revision feels helpful and is exactly how an approval ends up bound to a document nobody read. If the evidence moved, the decision has to be made again.

15 / definition of done

What must be true before the sheet is removed.

Acceptance criteria
  • A paused chair can be answered entirely inside the deck.
  • Every choice shown traces to a recorded chair result — the renderer adds no scientific text.
  • The answer resumes only the chair, in the exact originating conversation.
  • The owner can use another conversation and start another cycle while the first meeting waits.
  • Submit and verdict complete in the deck as two visible transitions.
  • All three verdicts write durable reviews with exact evidence and deck bindings.
  • Request changes carries the exact issue IDs and comment into the focused round.
  • Downloaded, legacy, wrong-thread, stale, superseded, hash-mismatched and consumed decks are read-only.
  • Arbitrary agent-generated HTML cannot cause a DBTL write.
  • Keyboard-only and assistive-technology users can navigate, select, comment, submit, retry, and understand the result.
Explicit non-goals
  • No model call creates or rewrites slide prose.
  • No direct API access in downloaded HTML.
  • No project-wide “waiting for you” lock.
  • No review sheet removed for non-Design stages.
  • No existing historical deck becomes interactive.
  • No one-click submit-and-review in v1.
  • No preflight roster/depth configuration moved into the deck.
A renderer or descriptor failure must never strand the owner without a visible, deterministic recovery action.
ACCEPTANCE · NON-GOALS16 / 18
The accessibility line is a real gate, not a courtesy. Once the deck is the only input surface, an inaccessible deck means an inaccessible approval, and the approval is the part of DBTL that is legally and scientifically load-bearing.

IMPLEMENTATION REFERENCE17 / 18
