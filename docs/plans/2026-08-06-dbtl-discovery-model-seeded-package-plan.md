# DBTL discovery: tool-seeded package plan

**Status:** Proposed; this document does not authorize implementation or rollout.

**Date:** 2026-08-06

**Goal:** Let the Lead Agent suggest a DBTL cycle from ordinary project chat
with a useful, evidence-labelled seed—without a hidden model call on every turn,
generic clarification questions, or new workflow authority.

**Parent plan:**
[`2026-08-01-conversational-dbtl-discovery-plan.md`](./2026-08-01-conversational-dbtl-discovery-plan.md)
owns discovery persistence, routing, confirmation, cycle creation, and rollout.
This plan changes only how conversation seeds a candidate package.

---

## 1. Problem

`deerflow.dbtl.discovery.build_discovery_package()` currently receives the
latest user text plus the previous stored dictionary. It safely produces a
deterministic seed, but its generic rationale, intended output, and regex-derived
open questions do not reliably reflect a long conversation.

The Lead Agent already reads the available conversation and project context.
Its understanding cannot simply be reused as structured data, however:

- forcing structured output would replace or distort the conversational reply;
- parsing the reply would make prose an authority boundary; and
- a second extractor would re-read the conversation through a hidden model call.

The missing boundary is an explicit, inspectable way for the Lead Agent to
propose a package during its normal turn.

## 2. Decision

Register one single-purpose Lead Agent tool named `dbtl_workflow`.

When the Lead Agent has enough evidence to recommend DBTL, it calls the tool
with a versioned discovery package. The structured arguments are generated by
the same model step that decides to propose the cycle. No tool call means no
discovery-specific extraction or compaction work.

The tool validates the package and emits a server-owned proposal marker. It
does **not** write a cycle or discovery record. After the Lead Agent returns,
the Supervisor may consume one valid marker, update the existing discovery
record, and append the existing revision-bound confirmation card.

Authority remains unchanged:

```text
Lead Agent proposes
    -> tool validates
    -> Supervisor persists and delivers
    -> human confirms
    -> existing Supervisor transaction creates one cycle
```

The tool cannot create or advance a cycle, select or run a stage, approve a
gate, answer another control, or promote knowledge.

The deterministic classifier remains a cheap routing signal. Explicit cycle
requests still enter discovery directly. The tool adds a model-initiated route
from ordinary chat; it does not replace routing precedence, decline
suppression, or an explicit **Ordinary project work** choice.

## 3. Product behavior

### 3.1 Availability

Expose `dbtl_workflow` only when the run is:

1. authenticated, interactive, and project-scoped;
2. eligible for graph-backed conversational discovery;
3. not explicitly scoped to ordinary work; and
4. not waiting on another server-owned DBTL control.

It is available to the eligible Lead Agent in ordinary and discovery branches.
It is absent from subagents, stage workers, review meetings, and scheduled or
other non-interactive runs.

### 3.2 Proposal threshold

The tool description tells the Lead Agent to call it only when the available
context contains:

- a concrete objective or decision;
- at least one intended artifact or observable result; and
- a reason that explicit Design, Build, Test, and Learn boundaries would reduce
  risk or improve reproducibility.

Keywords such as “reproducible,” “audited,” “notebook,” or “experiment” are
supporting evidence, not sufficient triggers. Read-only questions, explanations,
and small errands remain ordinary unless the person explicitly requests a cycle.

### 3.3 Human experience

After a valid proposal, the Lead Agent briefly explains why DBTL may help. The
existing discovery card shows the seed and offers:

- **Start DBTL cycle**;
- **Keep discussing**; and
- **Continue as ordinary work**.

Corrections happen in chat. The card is a review and decision surface, not an
editable setup form. No cycle exists before **Start DBTL cycle** succeeds.

### 3.4 Questions

A package may carry at most five open questions, ordered by design impact. Each
question must name:

- the unresolved or contradictory decision;
- why it changes the design; and
- the package fields or later choices it affects.

The Lead Agent asks at most one per conversational turn. A fixed field label
such as “success criteria” or “target trait” is not a question. If a missing
field does not materially change the design, omit it rather than blocking the
proposal.

## 4. Package contract

Add `discovery_package.v2` to the existing JSON payload. A versioned parser
accepts v1 during rollback, but only valid v2 tool proposals may be
automatically offered.

| Field | Rule |
| --- | --- |
| `version` | Literal `2`. |
| `proposed_title` | Short human-readable title. |
| `objective` | Concrete question, decision, or outcome. |
| `rationale` | Why DBTL is useful for this work. |
| `known_inputs` | Bounded declared inputs or references. |
| `intended_outputs` | 1–10 concrete artifacts or observable decisions; never “a reviewed result for …”. |
| `success_criteria` | Bounded observable criteria; may be empty when not material yet. |
| `rejection_criteria` | Bounded disconfirming or stop criteria. |
| `conflicts` | Incompatible statements preserved without choosing a side. |
| `open_questions` | 0–5 structured material questions. |
| `provenance` | Per-field source and status. |
| `source_refs` | Bounded server-issued references already present in context. |

Provenance sources are `user_turn`, `project_evidence`, `memory_evidence`, and
`model_suggestion`. Status is `user_stated`, `evidence`, `proposed`, or
`conflicted`.

Rules:

- `user_stated` attributes a statement to the person; it does not mean the
  whole package is accepted.
- project and memory evidence never become human decisions.
- model suggestions remain proposed until card confirmation.
- the model may reuse only server-issued source references; invented references
  invalidate the package.
- confirmation binds the exact package hash without rewriting field provenance.
- a conflict prevents the affected field from being treated as settled.

Store v2 in the existing bounded discovery JSON. Add no table unless
implementation proves the current storage contract insufficient.

## 5. Context and cost boundary

Do not add a discovery-specific transcript window, summarizer, compactor, or
cross-cycle digest builder in this slice.

The Lead Agent uses its existing bounded context:

- recent messages and the durable conversation summary;
- project manifest/history when the existing discovery flag allows it;
- project/global memory when their existing flags allow it; and
- server-issued references from the current discovery context provider.

Heavy files, data, code, notebooks, and artifacts remain references. If the
available context no longer supports a claim, mark it proposed, ask for
confirmation, or omit it; do not pretend to cite inaccessible history.

The normal post-tool response may require the Lead Agent's usual tool-result
turn. That is visible tool use, not a separate hidden extractor.

## 6. Server flow and failure behavior

```text
eligible Lead Agent turn
    -> optional dbtl_workflow(package_v2) call
    -> validate shape, bounds, provenance, scope, and source refs
       -> invalid: bounded ToolMessage; no record, card, or cycle
       -> valid: one server-owned proposal marker
    -> Supervisor begins/revises the thread's discovery record idempotently
    -> existing readiness and offer policy run
    -> existing confirmation card is delivered
    -> human may create one cycle through the existing transaction
```

Only one valid marker is consumed per run. Equivalent calls deduplicate by
project, thread, run, and canonical package hash. A different second package in
the same run is refused.

Failure rules:

- **Malformed or premature call:** no card; return bounded validation guidance.
- **Missing material decision:** ask one real question in chat; do not
  automatically retry the tool.
- **Classifier false positive:** no tool call means no model-seeded proposal.
- **Unavailable retrieval:** continue with already-authorized context; never
  fall back to another project or user.
- **Contradiction:** preserve both sides and keep the affected field unsettled.
- **Stale or duplicate proposal:** reuse existing compare-and-set and delivery
  idempotency.
- **Ordinary-work decision:** preserve current suppression; a later explicit
  start still wins.
- **Pending control:** do not offer a new cycle over the outstanding decision.
- **Non-interactive run:** tool absent.

The tool result carries no Human Input artifact. The Supervisor alone mints the
card after validation.

## 7. Non-goals

- No hidden per-turn updater or classifier model.
- No parsing of Lead Agent prose into workflow state.
- No automatic model-repair loop for invalid tool arguments.
- No direct cycle creation or stage mutation from the tool.
- No editable setup form or new discovery repository.
- No separate context-compaction or knowledge-digest subsystem.
- No default-on rollout.

## 8. Phased implementation

### Phase 0 — contract and characterization

- Add fixtures for a detailed multi-turn experiment, answered questions,
  contradictory requirements, a read-only request, and a summarized thread.
- Pin current deterministic package behavior and default-off flags.
- Define and test the v2 parser, bounds, canonical hash, provenance, and
  source-reference validation.

**Exit:** package quality and authority rules are testable without a model or
database.

### Phase 1 — pure proposal tool

- Register the tool without repository or cycle authority.
- Return one validated proposal marker or bounded errors.
- Enforce project scope, interactive mode, pending-control exclusion, and one
  accepted marker per run.

**Exit:** the tool can validate a proposal but cannot mutate DBTL state.

### Phase 2 — Supervisor integration

- Consume markers from eligible ordinary and discovery Lead Agent runs.
- Begin or revise the existing discovery record through its repository port.
- Reuse existing readiness, offer policy, card/outbox delivery, decline
  suppression, and confirmation transaction.
- Keep deterministic v1 building for explicit rollback only; never auto-offer
  it as a model-initiated generic proposal.

**Exit:** one valid marker can produce one confirmation card; no tool call can
create a cycle.

### Phase 3 — package quality and dark pilot

- Encode concrete-output, material-question, conflict, and provenance rules in
  the tool description and discovery reminder.
- Record validation outcome and proposal source, not hidden prompts or model
  reasoning.
- Replay explicit, classifier-suggested, tool-suggested, declined, stale-card,
  pending-control, and ordinary scenarios in the manual profile.
- Review false/missed offers, question materiality, corrections, token/latency
  cost, duplicate cards, and accepted-package quality.

**Exit:** a documented human rollout decision exists. Implementation alone does
not enable any default-off flag.

## 9. Acceptance criteria

1. An eligible ordinary turn without a tool call performs zero
   discovery-specific model or compaction calls.
2. A valid call preserves concrete decisions and requested outputs from a
   multi-turn fixture.
3. Answered and generic questions are absent; every remaining question explains
   its design impact.
4. Contradictions remain visible and keep affected fields unsettled.
5. Invalid, duplicate, unauthorized, non-interactive, or pending-control calls
   create no card and no cycle.
6. The Lead Agent still returns ordinary prose; package JSON is not rendered as
   its reply.
7. One valid proposal produces at most one card through the existing
   server-owned delivery path.
8. No cycle exists before human confirmation; retries create at most one cycle.
9. Source references are bounded, server-issued, and project-authorized.
10. Existing explicit discovery, ordinary override, decline suppression,
    inspection, and rollback remain compatible.
11. Heavy project inputs remain references rather than model context.
12. Manual evidence is reviewed before any rollout flag becomes default on.

## 10. Alternatives rejected

- **Force structured output on the Lead invocation:** conflicts with its normal
  conversational reply.
- **Parse the Lead reply:** makes prose a workflow input and authority boundary.
- **Run a hidden extractor:** duplicates understanding and adds cost/latency.
- **Keep generic deterministic auto-offers:** stable but fails the package-quality
  goal; retain only as explicit rollback.

## 11. Review checkpoint

- **Decision:** Carry the model-seeded package through a scoped
  `dbtl_workflow` proposal tool.
- **Authority:** Lead proposes; tool validates; Supervisor persists/delivers;
  human confirms; existing transaction creates.
- **Cost:** No tool call means no discovery-specific model work.
- **Primary risk:** Under- or over-invocation by the Lead Agent; contain through
  dark flags and human-reviewed pilot metrics.
- **Rollback:** Hide the tool and retain explicit deterministic discovery.
- **Next step after approval:** Convert Phases 0–3 into agent-ready tasks; do not
  implement directly from this document.
